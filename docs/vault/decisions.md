| **`CrossEnvironmentGrants` se elimina; los permisos entre miembros son los grants y `linkOrigin` de T3** | (d) Un link se empareja con acceso `read-only`/modo/`full-access` elegido por quien aprueba (`PeerLinks.testkit.ts linkTo(access)`, `McpOAuth` approval). Por debajo de full-access, el trabajo del link queda en el `linkOrigin` y no toca hilos propios ni de otros links (`apps/server/src/mcp/linkOrigin.ts:36-60`, `docs/internals/remote.md` "Work a link paired below full access"). Full-access es un grant explícito del dueño del agente (código de pairing del destino) y T3 lo documenta como no fenceado: el agente corre como el usuario receptor. Eso expresa nuestra regla "sin full-access ajeno sin grant explícito". Límite: un link es entre dos environments con un código del destino; no hay delegación hub-mediada, así que "pedir acceso a otra área lo aprueba el admin" es política nuestra en la bandeja de propuestas: al aprobar, el hub entrega al solicitante un código de pairing del miembro destino (o el destino lo emite). No mantener un segundo sistema de permisos.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## Recomendadas (aceptadas en principio, el plan las usa)

| Decisión                                                                 | Razón                                                                                                                                                    |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Hub = un server T3 en modo enterprise**                                | T3 ya trae transporte, auth de environments, `/mcp`, peer links y delegación remota. Un servicio aparte las reconstruiría                                |
| **Un solo store de empresa persistente en el hub**                       | Hoy hay tres copias en memoria de "quién está en qué equipo" ([current-state.md](current-state.md))                                                      |
| **Knowledge = repo git de `.md` en el hub** (`global/`, `areas/<team>/`) | Historial, diff y revert gratis; "qué cambió entre la corrida 1 y la 2" es la evidencia del loop. Promover área→global = commit aprobado que mueve texto |
| **Una sola bandeja de propuestas**                                       | El mismo mecanismo para: knowledge nuevo, mover de scope, quitar, pedir acceso a otra área                                                               |
| **Por eventos, no always-on**                                            | Más barato, reproducible para evals, no quema la suscripción de nadie                                                                                    |
| **Rol líder de área**                                                    | Las aprobaciones de área dependen de él; hoy solo existe `isAdmin`                                                                                       |
| **Stats de uso: fuera de la base**                                       | No bloquean el loop                                                                                                                                      |
| **Ingesta no inyecta todo al prompt**                                    | Norai probó que el mapa solo pierde contra el repo crudo; el knowledge es índice + lo que no está en ningún repo                                         |

## Descartadas

- **Servicio de knowledge totalmente aparte de T3:** duplica auth y transporte.
- **Memorias separadas por nivel como sistemas distintos con agentes negociando tasks:** más maquinaria. El scope es un folder/atributo; mover es un commit aprobado.
- **Onboarding real con OTP y Google para la base:** se finge con seed y auth falsa.
- **Full access a agentes ajenos sin grant explícito:** otra persona manejaría un agente con tus credenciales.
